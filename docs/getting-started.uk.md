# Початок роботи з keel

[English](getting-started.md)

Цей посібник веде вас від встановлення до завершеної задачі, задачі, що триває наступного дня, і
фічі, спланованої до будь-якого коду.
keel — це плагін для Claude Code (сьогодні Claude Code є платформою; інших агентів для програмування
заплановано). Ви вводите кілька команд, а keel планує, перевіряє й веде облік навколо вашої роботи.

Після команди ви пишете, чого хочете, звичайними словами (`/keel:end-task передай`); коли keel не
певен, він перепитує. У keel три способи працювати, задачі, сесії й планування, і в одній розмові
вони не змішуються: дивіться [способи працювати](workflows.uk.md). Усі команди та їхні варіанти:
[команди](commands.uk.md).

## 1. Вимоги

Claude Code, Node.js 22 або новіший (`node --version`), git і Windows, macOS або Linux. Подробиці:
[встановлення](install.uk.md#вимоги).

## 2. Встановлення

У Claude Code: `/plugin marketplace add mvbsoft/keel`, потім
`/plugin install keel@keel`. Claude Code питає два налаштування (мову, якою говорить keel, і чи можуть
агенти keel працювати на Opus) та область встановлення. keel діє лише в проєктах, які ви налаштуєте
на наступному кроці. Встановлення з термінала, області встановлення, оновлення й видалення:
[встановлення](install.uk.md).

## 3. Налаштування проєкту: `/keel:configure`

Відкрийте проєкт у Claude Code і запустіть:

```
/keel:configure
```

Спершу keel питає, налаштовуєте ви цей проєкт чи лише цей ПК, а для нового проєкту — яке
налаштування ви хочете: **швидке** (рекомендовано, близько шести питань) чи **докладне**. keel
потрібен репозиторій git: у папці без нього він пропонує `git init` і перший коміт поточного стану, а
якщо ви відмовитеся, зупиняється. Далі він працює за такими кроками.

**Що він сканує.** Мови, менеджери пакетів, частини монорепозиторію, команди тестів, лінтера й
перевірки типів (з CI, скриптів, запускачів задач, хуків, конфігурацій інструментів), наявні правила
для ШІ (AGENTS.md, CLAUDE.md тощо) і сканери безпеки. Файли з секретами перелічуються лише за шляхом:
сканер їх не відкриває, і Claude має інструкцію їх не відкривати.

**Про що він питає.** Перед кожною групою питань keel кількома простими рядками пояснює, що це
за налаштування, на що воно впливає, дає приклад і каже, як змінити його пізніше; далі варіанти з
плюсами й мінусами та рекомендація. Кожне рішення — окреме питання, тож перед вами всі варіанти;
рекомендований стоїть першим, і ви завжди можете написати власну відповідь. Попросіть більше — і keel
пояснить налаштування повністю. Швидке налаштування теж пояснює; воно лише питає менше.

- **Швидке налаштування** питає лише: дві мови (якою keel говорить і якою пише в репозиторій),
  команди гейтів (команди, які мають пройти) і один пробний їх запуск, режим git і головну гілку,
  рекомендовані налаштування Claude Code (усі, по одному або жодного), а коли на цьому ПК ще немає налаштувань
  витрат — як він платить, статус-рядок і сторінку витрат. Усі інші значення — рекомендації keel;
  підсумок перелічує кожне з командою, яка його змінює, наприклад `/keel:configure verification`.
- **Докладне налаштування** проходить усі розділи: мови, гейти, сканери безпеки, git, пороги
  перевірки, розмір коду й коментарі, плагіни стеку, документація, перехід з іншої системи нотаток,
  налаштування Claude Code та витрати. Деякі розділи можна пропустити; мову репозиторію, гейти, git,
  пороги, розміри файлів і рівень коментарів та профіль документації пропустити не можна, але можна
  прийняти пропозицію однією відповіддю.

Пробний запуск пропускає будь-яку команду, яка розгортає, публікує, мігрує, видаляє або відкидає
незакомічену роботу (як-от `git restore`, `git stash` чи `rm`); keel пояснює чому, і ви можете
запустити її самі.

**Ваша наявна документація.** Швидке налаштування лишає її як є (пропонуються профіль документації й
шаблон). У докладному налаштуванні (профілі документації 3 і 4 обирають шаблон, як-от Diátaxis чи
arc42), коли обраний шаблон не той, за яким зараз написано вашу документацію, keel каже, що куди
переїде, і дає вартість як оцінку разом із тим, як її отримано: символи документації ÷ 4 × 3 токени
(читання, запис, перевірка) за ціною Sonnet, плюс перевірка Standard, у вигляді діапазону.
Перенесення виконується як звичайна задача keel: власна гілка, план, який ви схвалюєте,
виконавці на Haiku для перенесень, Sonnet для змісту й посилань, потім перевірка Standard. Після
вашого «так» keel готує файл задачі `.keel/local/docs-migration.md`, а підсумок налаштування каже
спершу запустити `/keel:start-task .keel/local/docs-migration.md`, щоб нова документація одразу
лягала в нові місця. Коли документація вже відповідає шаблону, keel каже, що переносити нічого.

Скорочений приклад швидкого налаштування:

```
keel: Я знайшов проєкт Node з npm. Гейти: тести `npm test` (з package.json),
      лінтер `npm run lint` (з CI). Запустити їх один раз, щоб перевірити, що вони працюють?
ви:   Так.
keel: Обидва пройшли. Режим git: хто комітить і пушить. Вручну: я даю звіт і готове
      повідомлення коміту, комітите ви. Автономно: я комічу, оновлюю гілку з main,
      знову запускаю тести й пушу; зливаю лише на ваше прохання. Змінити можна пізніше:
      /keel:configure git.
      1. Режим git? Вручну (раджу для першого проєкту) / Автономно
      2. Головна гілка? main (раджу, типова гілка репозиторію) / інша
ви:   1 Автономно, 2 main.
```

**Що він пише.** Лише після вашого «так», і спершу показує файли:

| Файл | Що |
|---|---|
| `.keel/config.json` | налаштування проєкту (у git, спільне з командою) |
| `.keel/profile.json` | підтверджений профіль проєкту (частини, тригери, секретні файли лише за шляхом) |
| `.keel/.gitignore` | тримає тимчасові файли keel поза git |

За бажання, кожне лише з вашого «так»: рекомендовані ним налаштування Claude Code для цього проєкту
або для всього ПК (спершу зберігається резервна копія кожного файлу), статус-рядок, короткий розділ
«Working with Claude Code» у вашому README і приватна сторінка витрат
([панель витрат](usage-dashboard.uk.md)).

**Коміт налаштування.** Кроки git у keel ніколи не комітять у головну гілку, тож наприкінці keel
пропонує два шляхи, в обох режимах git:

- закомітити нові файли `.keel/` (і README, CLAUDE.md, `.gitignore` чи файл налаштувань Claude Code,
  якщо налаштування їх змінило) у головну гілку самостійно: keel дає готові команди;
- або лишити їх незакоміченими: перший `/keel:start-task` запропонує забрати їх у гілку цієї задачі,
  тож вони потраплять у головну гілку з її злиттям (зручно, коли головна гілка приймає зміни лише
  через pull request).

Потім почніть першу задачу в новій розмові (`/clear`): робочі стандарти keel завантажуються, коли
розмова починається в налаштованому проєкті. Якщо в проєкті чи в `~/.claude` вже були власні
інструкції (довгий CLAUDE.md, правила, навички, команди, агенти), keel радить один раз запустити
`/doctor prompt-audit` і пояснює чому: коли дві інструкції кажуть протилежне, Claude довільно обирає
одну з них, а застарілі інструкції забирають контекст у кожній розмові. Ця команда Claude Code
показує суперечності, застарілі інструкції й посилання на відсутні файли, кожне із запропонованою
правкою, і нічого не змінює без вашої згоди. Якщо таких інструкцій немає, keel про неї не згадує.
Кожна інша команда keel, крім `/keel:help` і `/keel:usage`, спершу перевіряє це налаштування й
пропонує його запустити.

## 4. Ваша перша задача: `/keel:start-task`

```
/keel:start-task https://example.atlassian.net/browse/CAN-123
```

Джерелом може бути посилання (Jira, Linear, Asana, issue GitHub, Google Docs або будь-яка сторінка),
ключ на кшталт `CAN-123`, шлях до файлу або ваші слова. Посилання читається ззовні (конектором, `gh`
або веб-запитом; якщо не вдалося, keel просить вставити текст). Ключ шукається всередині, спершу в
задачах keel, потім у репозиторії, і keel питає «Це вона?»; сам по собі `#123` ніколи не читається з
GitHub, тож дайте посилання на issue. Шлях до файлу — keel читає файл. Ваші слова — це текст задачі
(keel ще шукає схожі незакінчені задачі). Далі keel:

1. **Переказує задачу:** мету, як зрозуміємо, що готово, і що не робимо. Він перевіряє в коді, що
   задача вважає даністю; якщо щось не так, каже про це з `file:line`. У тому самому повідомленні
   питає «нова чи продовження?» (коли незакінчених задач немає: «тож це нова. Правильно?»).
2. **Дає назву:** ідентифікатор (`CAN-123` або короткий на кшталт `fix-reset-500`), заголовок і опис
   одним рядком, щоб ви погодилися або змінили.
3. **Питає** про те, чого не може знайти в коді, по 1-3 питання за раз. Коли мета розмита або є
   кілька справжніх способів зробити, натомість пропонує брейншторм і починає його лише з вашого «так».
4. **Планує.** Проста задача (один модуль, жодного нового публічного інтерфейсу, жодного
   архітектурного вибору, від одного до трьох файлів) отримує короткий план у чаті й питання
   «Почати?» разом із гілкою, де працювати (нижче). Складна задача отримує **Plan Mode**: файли не
   змінюються, доки ви не схвалите план. План називає файли, де житиме кожна нова річ, що вже дають
   фреймворк або встановлені пакети, тести, документацію, яку треба оновити, і ймовірний рівень
   перевірки (наприкінці keel пропонує рівень за фактичною зміною, і він може відрізнятися). Великий
   план (типово 8 кроків або 15 файлів) ще й пропонує передати його кроки агентам-виконавцям;
   схвалення або зміна плану й є відповіддю, окремого питання немає
   ([економія витрат](cost-optimization.uk.md#5-пороги-делегування)). Якщо під час налаштування ви
   ввімкнули налаштування Claude Code «Yes, clear context», схвалення плану таким способом починає
   роботу в новій розмові лише з планом.
5. **Пише код**, крок за кроком, або через агентів-виконавців, коли так каже план.

Питання «Почати?» (або перший крок виконання в плані) також називає гілку, на якій ви зараз, і питає,
де працювати: нова гілка `<id>-<short-name>` від поточної (рекомендовано), поточна гілка або ваші
власні кроки git (наприклад, «перейди на dev, онови її, влий у неї main, потім створи гілку
NEW-FEATURE»). На головній гілці keel прямо каже, що зміни лишатимуться там до кроку git, коли keel перенесе їх у нову гілку (у головну гілку keel ніколи не комітить), і радить нову гілку одразу.

Після вашого «так» (або схвалення плану) keel виконує ваш вибір гілки в обох режимах git, бо ви
про це попросили: ваші власні кроки по одному, зупиняючись на конфлікті чи відмові; він ніколи не
пушить і не зливає в головну гілку, якщо ви цього не сказали. Потім створює на цій гілці папку
задачі `.keel/tasks/<id>/`. Незакомічені зміни спершу зупиняють його: keel питає, що з ними робити,
а коли це лише файли налаштування з `/keel:configure`, пропонує забрати їх у цю гілку. На власній
гілці папка лишається із задачею до її завершення й ніколи не потрапляє в головну гілку. Якщо ви
починаєте тікет, який уже є незакінченою задачею, keel натомість пропонує її продовжити.

## 5. Завершення задачі: `/keel:end-task`

```
/keel:end-task
```

keel питає, що робити: 1) завершити повністю, 2) передати в іншу розмову, 3) своя інструкція. Можна
сказати одразу: `/keel:end-task заверши`. Щоб завершити, keel запускає гейти (тести, лінтери, типи,
сканери), пропонує рівень перевірки за зміною й просить вас обрати: лише гейти, Basic, Standard,
Maximum або без перевірки. Рівень можна й назвати: `/keel:end-task заверши, рівень standard`. Рівні,
їхню вартість і те, що робить кожен, описано в [перевірці](verification.uk.md).

Потім він показує звіт і питає, що виправляти. До звіту keel змінює лише дві речі: діє за
примітками щодо коментарів у новому коді (додає відсутній коментар, скорочує задовгий) і виправляє
гейти, що впали через цю зміну. Усе інше чекає на вашу відповідь. Коли немає пунктів «обов'язково»
чи «бажано виправити», keel не питає й іде далі (пункт «можна виправити» ви все одно можете
попросити). Вигляд звіту (приклад, скорочено; формулювання й числа вигадані):

```
Рівень: Basic. Гейти: тести пройшли, лінтер пройшов, gitleaks не встановлено
(попередження: секрети не скановано).

Обов'язково виправити
1. [підтверджено] Порожній кошик покупок повертає 500 (src/cart/total.js:42)
   Що це: сума кошика покупок без товарів.
   Проблема: items[0] читається до перевірки довжини, тому порожній кошик покупок викликає виняток.
   Як виправити: спершу перевірити довжину й повернути 0.
   Якщо не виправити: сторінка оформлення замовлення падає для нових клієнтів.
   Моя думка: згоден.
Бажано виправити
2. [неясно] Знижка застосовується після податку (src/cart/discount.js:18)
   ...
Можна виправити (не перевірено): 3 перейменувати `tmp` у total.js, 4 застарілий коментар
у discount.js (докладно на запит)
Перевіряльники спростували 2 знахідки.
```

Ви відповідаєте щодо кожного пункту: виправити, пропустити або не проблема («виправити всі
обов'язкові, 4 пропустити» теж працює). keel виправляє обрані пункти по одному, знову запускає гейти
й дає новому перевіряльнику один раз перевірити кожен виправлений обов'язковий і бажаний пункт. Потім
сам Claude Code питає «keel: задачу <id> виконано? Її папка `.keel/tasks/<id>/` піде в кошик keel.»,
щоразу, навіть коли ви сказали «заверши повністю». Так → папка переїжджає в кошик keel (на цьому ПК,
поза git) перед комітом, тож у головну гілку вона ніколи не потрапляє. В автономному git крок git, що
зупинився до коміту, повертає папку, і задача лишається активною: ви виправляєте причину й знову
запускаєте `/keel:end-task`; крок, що зупинився після коміту (оновлення чи пуш), лишає прибирання
закоміченим: виправте причину, і keel виконає цей крок ще раз. У ручному git скажіть keel, якщо не
комітите, і він поверне задачу. Ні → задача просто лишається активною на своїй гілці, без кроку git:
працюйте далі й запустіть `/keel:end-task` знову або передайте її. Після «так» іде git:

- **Git вручну** (`git.mode`: `manual`, радимо для першого проєкту): keel не виконує жодного кроку
  git, про який ви не просили. Він дає вам змінені файли й готову команду коміту, яка включає
  прибирання папки задачі.
- **Git автономно**: keel робить коміт (секретні файли до нього не потрапляють), оновлює гілку з main
  і знову запускає тести, якщо з'явилися нові коміти, і пушить гілку. Зливає лише тоді, коли ви про
  це попросили, наприклад `/keel:end-task заверши й злий у main`; тоді Claude Code показує свій запит
  дозволу на злиття. З `git.ask_before_merge: false` в автономному режимі, підтвердженому на цьому ПК,
  завершення зливає без питань і без цього запиту. Без цього гілка лишається запушеною, і ви зливаєте
  її, коли будете готові. Якщо цільова гілка захищена, keel пропонує натомість створити pull request.
  Він ніколи не робить force-push і не комітить у main напряму, а гілку видаляє лише в
  `/keel:tasks drop`. Першого разу ви підтверджуєте автономний режим для цього проєкту на своєму ПК, і
  знову після зміни його налаштувань git.

Задача закінчується одним підсумковим звітом: що зроблено, таблиця перевірки, git, що далі й витрати
([приклад](workflows.uk.md#підсумковий-звіт); як рахуються витрати:
[панель витрат](usage-dashboard.uk.md)). Перед наступною задачею запустіть `/clear`: нова розмова
коштує менше за довгу, бо кожен запит перечитує всю розмову.

## 6. Робота, яка не вміщується в один день

Задачі й сесії підходять для двох видів такої роботи. Сторінка [способи працювати](workflows.uk.md)
описує всі випадки.

**Задача, яку ви відкладаєте** (перерва, спершу з'явився інший тікет). Коли ви зупиняєтеся, не
закінчивши задачу:

```
/keel:end-task передай
```

Підходять будь-які слова: «постав на паузу», «підготуйся до наступної розмови». keel перевіряє гейти
(вищий рівень лише якщо ви його назвете), а потім оновлює файл задачі: мета, наступна дія, стан
кожного кроку (зроблено, в процесі, зламано, не почато) і де робота, файли, рішення, що не
спрацювало, відкриті питання й як перевірити. Задача отримує `status: handed-off`. Git робить
передачу замість завершення: без злиття (автономно: коміт, пуш, повернення на базову гілку). Для
задачі, що працює без власної гілки (у головній гілці чи в своїй базовій), переданої без інструкції
щодо git, спершу ставиться питання, в обох режимах git: нова гілка звідси (рекомендовано), коміт і
пуш у поточну гілку (не на головній гілці), поки без коміту (зміни лишаються незакоміченими й переходять із вами, якщо ви
перемкнете гілку) або ваша власна інструкція; keel виконує відповідь. Пізніше, у будь-якій розмові:

```
/keel:start-task CAN-123
```

keel знаходить незакінчену задачу й питає «Це продовження CAN-123?». Якщо так, він переходить на гілку
задачі, читає файл задачі, каже, наскільки пішла вперед головна гілка (і пропонує її підтягнути) і що
змінилося після передачі, запускає команду перевірки задачі, знову читає тікет і розповідає, що
змінилося, а далі підсумовує й продовжує з наступної дії. `/keel:tasks` показує незакінчені задачі;
`/keel:tasks drop <id>` прибирає одну разом з усім, що вона лишила, кожну частину після вашого «так».

**Довга робота** (великий план, який будують день за днем в одному напрямку). Почніть із файлу плану
або з опису:

```
/keel:start-session plan.md
```

keel пише нотатку `.keel/next-session.md` (мета, план, список «Later» для того, що знайшли дорогою,
одна перша дія), показує її й питає «Почати?». Якщо так, він створює гілку для цієї лінії роботи (у
ручному git дає вам `git switch -c <name>` і чекає, доки ви скажете, що виконали). Нотатка
тримається в межах приблизно 150 рядків і ніколи не містить паролів, ключів чи токенів. Наступного
разу, у новій розмові:

```
/keel:start-session
```

keel читає нотатку, звіряє її з репозиторієм (нові коміти в main, інша гілка), у кількох рядках
розповідає, на чому ви зупинилися, і називає першу дію. Додайте інструкцію, щоб змінити спосіб:
`/keel:start-session сьогодні тільки тести`.

Завершуйте роботу кожного дня так:

```
/keel:end-session
```

Він перевіряє роботу цієї сесії, закомічену чи ні (рівень обираєте ви), оновлює нотатку та пам'ять
проєкту, пише журнал сесії, робить git (автономно: коміт і пуш; без злиття) і закінчує словами
«Наступного разу: ...», щоб ви погодилися або виправили. Кажіть, чого хочете, словами:
`/keel:end-session продовжимо завтра, підготуйся` запускає лише гейти, не питаючи про рівень;
`/keel:end-session запуш і злий у main` ще й зливає; `/keel:end-session цю лінію закінчено` позначає
лінію завершеною й виконує git як завершення (автономно: коміт, оновлення з головної гілки, пуш;
злиття лише тоді, коли ви про нього просите або `git.ask_before_merge` вимкнено). Без нотатки
`/keel:start-session` шукає плани й TODO і пропонує, що взяти; задачу сам ніколи не починає.

## 7. Спершу спланувати фічу: `/keel:start-planning`

Фічу, якій потрібно кілька задач, варто продумати до будь-якого коду. Планування — окрема розмова, і
коду воно не пише:

```
/keel:start-planning CSV-експорт рахунків
```

Першого разу в проєкті keel питає дві речі: мову тікетів і де лежить чернетка (на цьому ПК, поза git,
або в репозиторії, де її бачать колеги). Далі він переказує фічу, перевіряє в коді, на що вона
спирається, пропонує назву й ставить по одному питанню за раз. Ваші відповіді стають рішеннями, а
робота — короткими тікетами (T1, T2…) у чернетці. Без аргументу keel показує чернетки, які можна
продовжити. Поки розмова планує, keel відхиляє команди задач, сесій, configure і cleanup.

`/keel:end-planning продовжимо завтра` робить рев'ю змінених тікетів і записує, де зупинилося
планування; `/keel:start-planning <фіча>` продовжує звідти. `/keel:end-planning фінальне рев'ю й
перенесення` дає агентам-рецензентам перевірити тікети, які ще не пройшли рев'ю в теперішньому
вигляді, а потім увесь план; коли ви вирішите щодо кожної знахідки, keel переносить тікети в папку
фічі зі справжніми ключами на кшталт `PROJ-101`. Кроки git чекають на ваше «так».

Потім виконуйте тікети, кожен у новій розмові (`/clear`): `/keel:start-task наступний тікет` бере
наступний вільний тікет і пропонує гілку його фічі; далі це звичайна задача. Або
`/keel:start-session <фіча>` бере їх по одному в сесії. `/keel:tasks` теж показує
заплановані тікети. Усі випадки: [планування](workflows.uk.md#планування).

## 8. Прибирання: `/keel:cleanup`

```
/keel:cleanup
```

keel шукає тимчасові файли, резервні копії, кеші та те, що лишила стара система нотаток, і переносить
лише обране вами у свій кошик, `.keel/local/trash/`; нічого не видаляється. `/keel:cleanup restore`
скасовує перенесення. Усі варіанти: [команди](commands.uk.md#keelcleanup).
