# Рівні перевірки

[English](verification.md)

Коли ви запускаєте `/keel:end-task` або `/keel:end-session`, keel перевіряє вашу зміну перед комітом.
Є чотири рівні: від власних перевірок проєкту до повної команди агентів. keel пропонує рівень за
зміною; обираєте ви. Ця сторінка пояснює, що робить кожен рівень, як формується пропозиція, що
містить звіт і який рівень обрати. Сьогодні агенти — це субагенти Claude Code. Передача задачі
(`/keel:end-task передай`) або підготовка наступної сесії (`/keel:end-session продовжимо завтра,
підготуйся`) запускає лише гейти, якщо ви не назвете рівень. Передача ніколи не виправляє червоні
гейти: вона записує їх у файл задачі як відкриті питання.

Перевірці потрібен git, щоб бачити, що змінилося; у папці без git keel пропонує `git init`.
Невідстежувані файли, які вже були на початку задачі й не змінилися, — не робота цієї задачі: їх не
перевіряють і перелічують у звіті. Коли keel не має запису про початок задачі, він перелічує
невідстежувані файли й питає: «Чи всі вони належать до цієї задачі?»

## Чотири рівні

Спершу keel перевіряє коментарі нового коду за правилами коментарів і виправляє їх. Далі кожен рівень
запускає **гейти**: тести, лінтери, перевірки типів і сканери безпеки вашого проєкту (задаються в
`/keel:configure`). Сканер, який не встановлено, — це помітне попередження у звіті, а не збій. Червоні
гейти, які спричинила ця зміна, виправляються одразу. Якщо червоні гейти схожі на старіші за зміну,
keel питає: виправити їх спершу чи продовжити, позначивши звіт «гейти були червоними до перевірки».
Рівень визначає, які агенти працюють поверх гейтів.

| Рівень | Хто перевіряє | Перевіряльники (ліміт) | Хто зводить і ранжує |
|---|---|---|---|
| **Лише гейти** | жодних агентів | немає | немає |
| **Basic** | один універсальний рецензент (Haiku) | до 2, Sonnet | головна розмова |
| **Standard** | карта контексту (Haiku), універсальний рецензент, мисливець за помилками, архітектор, QA (також намагається зламати зміну), рецензент тестів, до 4 спеціалізованих груп | до 5, Sonnet; Opus для знахідок мисливця за помилками та групи безпеки | агент-суддя (Sonnet) |
| **Maximum** | карта контексту (Haiku), два мисливці за помилками на Opus (один на змінених рядках, один на зміні в контексті всього проєкту), архітектор на Opus, група безпеки завжди (Opus), інші активовані групи, разом до 4, QA на Opus, окремий QA «зламай це» (Sonnet), рецензент тестів | до 8, Opus; троє на кожну критичну знахідку, поки дозволяє ліміт | агент-суддя (Opus) |

Є також **без перевірки** (none): звіт каже «не перевірено».

Примітки:

- На рівні Basic архітектура — це перевірка розміру файлів, яку робить скрипт, без агента-архітектора, і
  жоден агент не запускає код (QA працює від Standard).
- Архітектор на рівні Standard працює на Opus, коли зміна має архітектурні сигнали (нові файли, файли
  понад попередження про розмір), інакше на Sonnet.
- На рівнях Standard і Maximum група документації працює завжди, коли змінений файл змінює
  поведінку; вона також перевіряє коментарі зміненого коду.
- Якщо `allow_opus` вимкнено, кожен агент вище, який мав би працювати на Opus, працює на Sonnet.
- Перед запуском можна додати або прибрати агента чи спеціалізовану групу. Попросіть «дешевше» або
  «глибше», і keel запропонує рівень зусиль (effort) для кожного агента.

### Що роблять агенти

| Агент | Що перевіряє |
|---|---|
| універсальний рецензент | один широкий прохід по зміні відносно її задачі: логіка, безпека, дані, документація, дублювання, назви, розмір, слабкі тести |
| мисливець за помилками | логічні помилки, проблеми під навантаженням, дублікати фреймворку, неправильне використання API |
| QA | запускає змінену функціональність і перевіряє критерії приймання; повідомляє про збої з командою для відтворення |
| QA «зламай це» | пробує межі, порожній ввід, нуль/один/багато, дозволи, переривання, паралельність |
| архітектор | де лежить кожна нова річ, розмір і ріст, дублювання, мертвий код, назви |
| рецензент тестів | чи зловили б тести те, що зміна щось зламала; доводить ключові тести, скасовуючи зміну й дивлячись, як вони падають |
| карта контексту | складає для інших агентів карту файлів, пов'язаних зі зміною |
| група безпеки | простежує ввід до небезпечних операцій; намагається обійти бізнес-правила |
| група даних | зміни бази даних і міграції, сумісність API, перевірка вводу, продуктивність |
| група середовища | залежності (потреба, lock-файли, ліцензії, довіра), інфраструктура (Docker, CI, розгортання, конфігурація, секрети) |
| група документації | документація й коментарі відповідають коду, правила коментарів, вимоги виконано без зайвого |

Агенти, що лише читають, не можуть писати. Агенти, що запускають код (QA, «зламай це», рецензент
тестів), працюють один за одним, і після кожного keel порівнює робоче дерево (відстежувані файли й
невідстежувані, яких git не ігнорує) зі знімком. Якщо щось змінилося, він зупиняється й пропонує
відновити. QA-агенти можуть писати лише в `.keel/local/tmp/qa/`; будь-який інший шлях хук відхиляє.

## Як keel пропонує рівень

keel обчислює пропозицію за зміною. Він перевіряє рядки згори, і перший збіг перемагає.

| Сигнал | Пропонує | Налаштування (`.keel/config.json`) | Типово |
|---|---|---|---|
| міграція бази даних | Maximum | немає | немає |
| доданий код, що масово видаляє дані: SQL `DROP` чи `TRUNCATE`, `DELETE` без `WHERE` у тому самому рядку, масове видалення через ORM (`deleteMany`, `destroyAll`, `delete_all`, `dropColumn` тощо) | Maximum | немає | немає |
| грошове слово або слово безпеки (див. нижче) у доданому коді файлу, що відповідає шляхам безпеки проєкту | Maximum | немає | немає |
| зміна має стільки рядків або більше | Maximum | `verification.tier_rules.very_large_change_lines` | 1000 |
| зміна поведінки у файлі, який імпортує стільки нетестових файлів (ключовий код) | Maximum | `verification.tier_rules.core_fan_in` | 5 |
| зміна має стільки рядків або більше | Standard | `verification.tier_rules.large_change_lines` | 400 |
| зміна зачіпає більше за стільки модулів | Standard | `verification.tier_rules.basic_max_modules` | 1 |
| активовано групу безпеки | Standard | немає | немає |
| стільки файлів або менше, і жоден не змінює поведінку (текст, коментарі, документація) | Лише гейти | `verification.tier_rules.gates_only_max_files` | 1 |
| усе інше | Basic | немає | немає |

Зміна, що зачіпає дані, API чи залежності (група даних чи середовища), однаково пропонується для Basic,
з причиною, яка це називає: на тестовому наборі список «обов'язково або бажано» у Basic збігся зі
списком Standard приблизно за сьому частину ціни. Оберіть Standard, коли хочете для неї
рецензентів-спеціалістів.

**Що виміряно, а що — судження.** Виміряно на тестовому наборі: зміни даних, API й залежностей
лишаються на Basic, а рецензент Basic працює на Haiku. Судження, не виміряне з keel: усі рядки
Maximum, більше одного модуля, група безпеки, пороги 400 і 1000 рядків; вони стоять там, де пропущений
дефект коштує найдорожче (гроші, доступи, дані, код, від якого залежить багато файлів). На тестовому
наборі список «обов'язково або бажано» у Basic збігся зі списком Standard на зміні будь-якого
розміру, і на зміні з 1083 рядків теж.

Що активує спеціалізовану групу:

- **безпека**: змінений файл у шляхах безпеки проєкту; або доданий код зі словом безпеки:
  `password`, `secret`, `api key`, `private key`, `bearer`, `jwt`, `oauth`, `csrf`, `authorize`,
  `authenticate`, `permission`, `is_admin`, `has_role`, `can_access`; виклик, що виконує код чи
  команди (`eval`, `exec`, `spawn`, `system`, `popen`, `unserialize`, `pickle.loads`, `yaml.load`);
  HTML-приймач (`innerHTML`, `dangerouslySetInnerHTML`, `v-html`); слабке хешування чи випадковість
  (`md5`, `sha1`, `createCipher`, `Math.random`); або рекурсивне видалення файлів (`rm -rf`,
  `shutil.rmtree`, `fs.rm` чи `fs.rmSync` з `recursive: true`). Видалення файлів видаляє файли, а не
  дані, тож воно пропонує Standard, а не Maximum; група безпеки перевіряє, яким може бути видалений
  шлях.
- **дані**: міграція, файл схеми чи моделі (`.sql`, `models/`, `entities/`, `schema/`,
  `schema.prisma`), файл API (маршрути, контролери, ендпоінти, обробники) або шляхи даних проєкту.
- **середовище**: маніфест залежностей чи lock-файл або шляхи середовища проєкту.
- **документація**: текстовий файл, файл у `docs/` або шляхи документації проєкту.

Спеціалізовані групи працюють на рівнях Standard і Maximum; пропозицію підвищує лише група безпеки.

Слова у вмісті читаються лише в доданих рядках коду: тестові й текстові файли не рахуються. Грошове
слово (`price`, `amount`, `balance`, `currency`, `payment`, `refund`, `invoice`, `payout`, `charge`,
`discount`, `vat`, `tax_rate`) поза шляхами безпеки не активує жодної групи: воно лише з'являється
серед сигналів зміни. Шляхи проєкту для кожної групи лежать у `.keel/profile.json` (`triggers`);
змінити їх можна через `/keel:configure scan`. Причина для Standard називає, що активувало групу,
наприклад `security group triggered (code src/auth.js: ...)`.

Рядки — це додані плюс видалені. Lock-файли, згенеровані файли та вендорні файли не враховуються: вони
нічого не кажуть про розмір роботи. Кількість перевіряльників на рівень задає
`verification.verifier_caps` (типово 2, 5, 8 для Basic, Standard, Maximum). Ліміти ходів
агентів задано у файлах агентів (60 для агентів-рецензентів, 350 для виконавців), а не в
конфігурації.

Усе це налаштовується; повний список дивіться в [налаштуваннях](settings.uk.md#цей-проєкт). Пропозиція
завжди йде з причинами, а рівень обираєте ви.

## Що роблять перевіряльники і суддя

Кожен агент, який повідомляє про знахідку, дає їй серйозність: критична (обов'язково виправити), важлива
(бажано виправити) або незначна (можна виправити). Знахідка потребує місця, конкретного випадку,
реального наслідку й перевірки, що її вже не покриває жоден захист. Агент, який не певен, що проблема
справжня, або не подає її, або подає з тією серйозністю, яку вона мала б, якби була справжньою, і каже,
що це з'ясувало б, щоб її перевірив перевіряльник. Серйозність сумнівної знахідки він ніколи не
знижує: незначні знахідки не перевіряються.

1. **Перевіряльники.** Окремий агент-перевіряльник намагається спростувати кожну критичну й важливу
   знахідку, поки дозволяє ліміт рівня: він переформульовує твердження, сам читає код і перевіряє його
   за чотирма гейтами (досяжність, реальний вплив, відсутність наявного захисту, конкретний випадок).
   Його вердикт — підтверджено, спростовано або неясно, з доказом `file:line`.
2. **Кого перевіряють.** Знахідки в одному місці (часто одна проблема, про яку повідомили кілька
   агентів) ділять один запуск перевіряльника, до 4, критичні теж; кожна все одно отримує власний
   вердикт. Критичні знахідки йдуть першими, кожна з власним запуском. На рівні Maximum критична
   знахідка отримує три запуски з різними поглядами (досяжність, вплив, захист), поки ліміт лишає
   кожній критичній знахідці хоча б один: її підтверджено, коли двоє з трьох її підтверджують,
   відкинуто, лише коли двоє з трьох її спростовують, а інакше показано як неясну. Інші важливі
   знахідки йдуть до 3 на запуск, з тією самою моделлю перевіряльника, за файлом, а потім за папкою.
   Незначні знахідки не перевіряються. Те, що не вміщується в ліміт, показується як «не перевірено» з
   причиною.
3. **Знахідки QA.** Знахідка QA з командою для відтворення минає перевіряльників, а важливу знахідку в
   тому самому місці вдруге не перевіряють. Натомість головна розмова знову запускає команду, коли
   перевірка команд keel каже, що її безпечно запускати. Якщо вона не падає так, як описав QA,
   знахідку показано як неясну; якщо падає — як доведену QA. Команду, яку перевірка відхиляє, не
   запускають, і знахідка лишається доведеною QA з приміткою «не запущено вдруге». Перевірка також
   відхиляє команду, що відкинула б зміну, яку перевіряють (наприклад, `git restore`, `git stash`,
   `git reset`, `git checkout --`, `find -delete`, `rm` чи `mv`), а keel порівнює робоче дерево до й
   після повторних запусків: будь-яка різниця зупиняє перевірку, так само як після агента, що
   запускає код.
4. **Суддя** зводить дублікати, відкидає спростовані знахідки, ставить суперечності поруч, сортує за
   серйозністю й нумерує список. Власних знахідок він не додає. На рівні Basic цю роботу
   робить головна розмова.
5. **Думка головної розмови.** До кожного пункту головна розмова відкриває код і каже «згоден» або
   «не згоден, бо ...». Вона не приховує незгоди з підтвердженою знахідкою. Проблема, яку головна
   розмова сама помічає під час читання, потрапляє до списку окремим пунктом із позначкою «не
   перевірено (сесія)».

## Звіт

keel показує результат простими словами. Коли є пункт «обов'язково» чи «бажано», він зупиняється й
чекає вашої відповіді, також коли ви назвали рівень заздалегідь. Коли таких пунктів немає, він не
питає, що виправляти: показує рядок «можна виправити» й іде далі, а ви все одно можете попросити
виправити пункт із нього. Окрім виправлень коментарів і червоних гейтів, описаних вище, жодного коду
не змінюється, доки ви не оберете.

| Частина | Що ви бачите |
|---|---|
| Обов'язково виправити | пронумеровані пункти докладно: що це, проблема, як виправити, що буде, якщо не виправити; його статус (підтверджено, доведено QA, неясно, не перевірено, не перевірено (сесія)) і думка головної розмови |
| Бажано виправити | те саме |
| Можна виправити | один рядок із позначкою «не перевірено»: номери й короткі назви; подробиці на запит |
| Суперечності | дві знахідки, виправлення яких конфліктують, поруч |
| Не перевірено | пункти з причиною та скільки знахідок спростували перевіряльники |
| Попередження | сканери, яких не встановлено, гейти, що були червоними раніше, неповні агенти, QA не запускав застосунок |

Ви відповідаєте щодо кожного пункту: виправити, пропустити або не проблема. keel виправляє обрані
пункти по одному, а потім:

- знову запускає гейти;
- створює нового перевіряльника для кожного виправленого обов'язкового чи бажаного пункту, щоб
  **перевірити** виправлення ще раз (один раунд);
- показує кожен пункт, про який повторна перевірка каже, що він досі є, і ви вирішуєте.

Підсумковий звіт `/keel:end-task` або `/keel:end-session` показує перевірку таблицею: для кожної
важливості — скільки знайдено, виправлено й лишилось, далі пункти, що лишилися, за номером і назвою,
рядок гейтів і попередження; його блок «Витрати» показує, скільки коштувала вся сесія, по кожному
агенту ([приклад](workflows.uk.md#підсумковий-звіт)). Коли працювали лише гейти, це один рядок
гейтів. Якщо ви знову просите той самий або нижчий рівень на точно тому самому коді, keel радить
цього не робити: результат буде той самий, а вартість приблизно така сама. Завершеній задачі потрібна
записана перевірка (вибір «без перевірки» теж записується); вона лишається чинною після коміту
перевіреного коду, а будь-яка інша зміна потребує нової.

## Вартість

Коли ви обираєте рівень, keel показує приблизну оцінку для кожного; звіт наприкінці показує справжню
вартість по кожному агенту. Числа нижче **виміряні**, а не вигадані: кожне — це справжній прогін keel
на тестовому проєкті, а розділи після таблиці кажуть, на чому і як. Час від часу вони змінюються, бо
виміри повторюються на нових версіях keel і з новими цінами моделей. Прогони йшли на keel 1.0 до його
останнього виправлення, яке дало QA-агентам інструмент Write для допоміжних скриптів (менше запитів
дозволу, ті самі перевірки); оцінювала окрема модель, без перевірки людиною.

### Виміряно в жовтні 2026 (keel 1.0)

| Рівень | Оцінка, яку показує keel | Вартість однієї зміни: середня, медіана (найменша-найбільша) | Знайдено дефектів (із 17, середнє на прогін 8 змін): з будь-якою важливістю / у «обов'язково або бажано» | Хибні тривоги серед «обов'язково або бажано» |
|---|---|---|---|---|
| Лише гейти | ≈$0.2 | $0.21, $0.20 ($0.18-0.27) | 0.7 / 0.7 | 0 на 24 прогони |
| Basic | ≈$0.25-0.5 | $0.34, $0.34 ($0.25-0.41) | 15.3 / 15.0 | 0 на 24 прогони |
| Standard | ≈$1.4-4.3 | $2.38, $2.00 ($1.39-4.30) | 16.3 / 15.0 | 1 на 24 прогони |
| Maximum | ≈$2.7-7.6 | $4.97, $4.74 ($2.72-7.60) | 17 / 14 | 0 на 8 прогонів |

**На чому.** 8 змін від 73 до 1083 рядків, усі на JavaScript, із 17 відомими дефектами: 3 справжні
баги з двох проєктів з відкритим кодом (ws: 1, Express: 2; доведені власними виправленнями цих
проєктів), 11 вписаних у три зміни для тесту (кожен доведено скриптом, що падає), 3 тонкі дефекти в
природній зміні (знайдені й доведені давнішим прогоном keel Standard, тож саме вони стали ключем
відповідей для цієї зміни, ключем, що може бути на користь Standard) і 2 чисті зміни без дефектів, щоб побачити, чи не вигадає keel дефект. До
змін додано приманки — правильний код, що виглядає неправильним. Кожну зміну прогнано 3 рази на
рівнях «лише гейти», Basic і Standard (24 прогони на рівень) і один раз на Maximum (8 прогонів), 80
загалом; з одним прогоном на зміну невеликі різниці Maximum — у межах шуму. 14 із 17 дефектів
знайдено в кожному прогоні Basic і Standard, тож числа розрізняють рівні переважно на 3 тонких; такий
малий і вузький набір показує, що keel
робить на цих змінах, а не загальний показник.

**Як оцінювали.** Окрема модель, яка не знала рівня, порівнювала фінальний список кожного прогону з
ключем відповідей. «Знайдено» — дефект, названий з будь-якою важливістю; знайдений наполовину рахується
як 0.5. Приманка, названа проблемою, — хибна тривога, коли вона потрапляє до списку «обов'язково або
бажано»; як пункт «можна виправити» вона не перевіряється й не рахується (Basic так зробив 2 рази,
Standard — 4).

**Як рахується вартість.** Claude Code записує кожен запит до моделі — головної розмови й кожного
агента — з токенами чотирьох видів (вхідні, запис у кеш, читання з кешу, вихідні). Кожен вид множиться
на прайсову ціну Anthropic для моделі, що відповіла, і все додається. Наприклад, прогін Standard за
$1.47 склався з $1.30 на Sonnet (головна розмова й більшість агентів), $0.16 на Opus і $0.01 на Haiku.
У частині Sonnet читання з кешу — більшість токенів (1.8 млн), але лише $0.18 грошей; вихідні токени
($0.56) і запис у кеш (близько $0.55) коштували більше. На підписці долари не
списуються: ті самі токени зараховуються до лімітів плану.

**Що входить у вартість.** Лише перевірка: від `/keel:end-task finish, level ...` до списку того, що
виправити (гейти, агенти, перевірка їхніх знахідок). Не входять: написання коду, виправлення знайденого
й перевірка виправлень, git, звіт про витрати. Кожен прогін починався у свіжій розмові. Та сама
перевірка Basic наприкінці розмови, в якій писали код (одна зміна, 2 прогони), коштувала $0.21
проти $0.26-0.29 у свіжій розмові на тому самому коді: та розмова вже містила змінені файли, була короткою (на старті
приблизно на 17k токенів більше), і її кеш ще був теплим. Довша розмова дорожча на кожному запиті: на
Sonnet кожні 100k токенів понад те додають приблизно $0.01 читання з кешу до кожного запиту (Basic
робить 10-13 запитів у головній розмові), а після паузи, довшої за життя кешу, уся розмова знову
записується в кеш, приблизно $0.25-0.40 за 100k токенів (обчислено з цін прайсу, не виміряно).

**Чим відрізняються рівні.** Справжні й вписані баги обидва рівні знайшли майже всі. Різниця — на зміні
з 3 тонкими дефектами: Basic знайшов там 4 з 9 за свої 3 прогони, Standard — 7 з 9; додаткові
знахідки Standard були пунктами «можна виправити», тож у списку «обов'язково або бажано» обидва знайшли
3 з 9. Standard також назвав більше справжніх проблем, яких не було в ключі (64 проти 39), приблизно в
7 разів дорожче. Maximum знайшов усі 17, і 3 тонкі теж, але 3 з них (2 тонкі, 1 вписаний) подав як
«можна виправити», тож у його списку «обов'язково або бажано» 14; він коштує приблизно вдвічі більше
за Standard і в 15 разів більше за Basic. На рівні «лише гейти» тести пройшли на кожній зміні; у 2 з 51
випадків (дефект × прогін) головна розмова сама помітила дефект, читаючи код, і назвала його своїм
неперевіреним пунктом. «Лише гейти» перевіряє, що нічого не зламалось; це не рецензування.

Порівняно з одним звичайним ШІ-рецензуванням (давніший прогін) Basic коштує приблизно
в 1.5 раза більше й знаходить приблизно стільки ж відомих дефектів; змінюється список виправлень: 2.7
пункти на прогін без хибних проти 5.5 на прогін у звичайного рецензування, з них 4 хибні за 8 прогонів.

### Для порівняння: звичайний рецензент без keel

Один звичайний рецензент на Sonnet, без keel, виміряний один раз на тих самих 8 змінах (один прогін на
зміну, давніша дата): $0.14-0.38 за зміну (у середньому $0.22), знайдено 15.5 з 17 дефектів, з 4 хибними
тривогами в його списку «обов'язково або бажано» за 8 прогонів.

## Який рівень коли

| Зміна | Рівень |
|---|---|
| звичайна зміна в одному модулі, також та, що зачіпає модель, API чи залежність | Basic |
| велика зміна, нова поведінка в кількох модулях, активована група безпеки (наприклад, код із паролями, токенами, дозволами, `eval` чи `innerHTML`, рекурсивне видалення файлів) або зміна моделі, API чи залежності, для якої ви хочете рецензентів-спеціалістів | Standard |
| міграція, масове видалення даних (`DROP`, `TRUNCATE`, `DELETE` без `WHERE`, масове видалення через ORM), код грошей чи доступу в шляхах безпеки проєкту, дуже велика зміна або ключовий код, від якого залежить багато файлів | Maximum |
| зміна в одному файлі без зміни поведінки (текст, коментарі, документація) | Лише гейти |

Пропозиція будується з тих самих сигналів ([що виміряно, а що — судження](#як-keel-пропонує-рівень));
обираєте ви. Типове значення в 400 рядків для «великої» зміни — емпіричне правило з досліджень код-рев'ю (люди-рецензенти знаходять
менше дефектів після 200-400 рядків), а не виміряне з keel: у тестовому наборі keel ([Вартість](#вартість))
кожен рівень знайшов кожен дефект і найбільшої зміни.

Більше про економію дивіться в [економії витрат](cost-optimization.uk.md).
