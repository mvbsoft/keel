# Команди

[English](commands.md)

Кожна команда keel: як її викликати і що відбувається в кожному випадку. Ці команди запускаєте лише
ви; модель ніколи не запускає їх сама.

**Як працюють інструкції.** Після команд задач і сесій ви пишете, чого хочете, звичайними словами;
окремих слів-аргументів немає. `/keel:tasks` (`drop`), `/keel:cleanup` (`restore`, `empty-trash`) і
`/keel:configure` (`machine`, назва розділу) приймають слова, показані нижче. keel розуміє, що ви маєте на увазі, перепитує, коли не певен, і перед кожною
дією одним рядком каже, що вона зробить. Слово рівня (`gates`, `basic`, `standard`,
`maximum`, `none`; `quick` означає `basic`) обирає рівень перевірки, коли стоїть окремо або після слова «рівень»
(`рівень standard`); про рівні: [перевірка](verification.uk.md).

| Команда | Коротко |
|---|---|
| [`/keel:configure`](#keelconfigure) | налаштувати або змінити keel для цього проєкту чи цього ПК |
| [`/keel:start-task`](#keelstart-task) | почати задачу або продовжити її |
| [`/keel:end-task`](#keelend-task) | завершити задачу або передати її |
| [`/keel:tasks`](#keeltasks) | список задач, одна задача або прибрати задачу |
| [`/keel:start-session`](#keelstart-session) | продовжити або почати довгу лінію роботи |
| [`/keel:end-session`](#keelend-session) | закінчити сесію: перевірка, нотатка, git |
| [`/keel:cleanup`](#keelcleanup) | перенести залишки в кошик keel, повернути їх, очистити старий кошик |
| [`/keel:usage`](#keelusage) | посилання на вашу приватну сторінку витрат, одразу відкрите |
| [`/keel:help`](#keelhelp) | коротка таблиця команд |

## `/keel:configure`

`/keel:configure [розділ | machine]`

Без `machine` кожен запуск спершу питає: цей проєкт чи лише цей ПК? keel потрібен репозиторій git: у
папці без нього `/keel:configure` і кожна інша команда пропонують `git init` і перший коміт поточного
стану, а на «ні» зупиняються.

| Ви вводите | keel робить |
|---|---|
| `/keel:configure` у новому проєкті | Питає: швидке налаштування (рекомендовано, близько шести питань) чи докладне. Сканує проєкт (мови, менеджери пакетів, частини монорепозиторію, команди тестів, лінтера й типів, CI, наявні правила для ШІ, сканери безпеки). **Швидке** питає дві мови, команди гейтів з одним пробним запуском, режим git і головну гілку, рекомендовані налаштування Claude Code (усі, по одному або жодного) і налаштування витрат, коли на цьому ПК їх немає; усі інші значення — рекомендація, а підсумок називає розділ, який їх змінює. **Докладне** проходить усі розділи: мови, гейти, git, пороги перевірки, розміри файлів і коментарі, плагіни стеку, документація, перехід з іншої системи нотаток, налаштування Claude Code, використання й витрати. Кожна група питань починається з простого пояснення (що це за налаштування, на що впливає, приклад); кожне рішення — окреме питання з усіма варіантами, рекомендований перший. Швидке лишає вашу наявну документацію як є; докладне, коли обраний вами шаблон документації відрізняється від того, за яким вона написана, пропонує підготувати її перенесення як задачу ([ваша наявна документація](getting-started.uk.md#3-налаштування-проєкту-keelconfigure)). |
| `/keel:configure` у налаштованому проєкті | Питає, що змінити: розділ, нове сканування чи все. |
| `/keel:configure`, коли конфігурація застаріла чи зламана | Виправляє її: питає лише про поля, які додав новіший keel, або перелічує кожну проблему з пропозицією виправлення, а решту лишає. |
| `/keel:configure machine` | Лише налаштування цього ПК, для всіх проєктів: мова розмови, значення ПК для налаштувань Claude Code, використання й витрати. Файлів `.keel/` не пише. |
| `/keel:configure <розділ>` | Лише цей розділ знову, у налаштованому проєкті. Розділи: `languages`, `scan`, `gates`, `git`, `verification`, `code`, `plugins`, `docs`, `migration`, `settings`, `usage`, `prices`. `prices` доручає агентові прочитати офіційну сторінку цін і показує різницю; `migration` переносить іншу систему нотаток у keel. |

Без вашого «так» нічого не пишеться. Налаштування проєкту пише `.keel/config.json`,
`.keel/profile.json` і `.keel/.gitignore`; з вашого «так» також рекомендовані налаштування Claude Code
(для кожного файлу спершу робиться резервна копія), короткий розділ «Working with Claude Code» у
вашому README, статус-рядок і приватну сторінку витрат. Наприкінці keel каже, як закомітити
налаштування (у головну гілку зараз або разом із першою задачею:
[коміт налаштування](getting-started.uk.md#3-налаштування-проєкту-keelconfigure)), і радить почати
першу задачу в новій розмові (`/clear`). Якщо ви погодилися перенести документацію, підсумок першою
називає цю задачу: `/keel:start-task .keel/local/docs-migration.md`. Кожна інша команда, крім
`/keel:help` і `/keel:usage`, спершу перевіряє це налаштування й пропонує його запустити. Усі налаштування:
[налаштування](settings.uk.md).

## `/keel:start-task`

`/keel:start-task <посилання | ключ | ваші слова>`

| Ви даєте | keel робить |
|---|---|
| посилання (Jira, Linear, Asana, GitHub, Google Docs, будь-яка сторінка) | читає ззовні (конектором, `gh` або веб-запитом); не вдалося → просить вставити текст |
| ключ або номер (`CAN-123`, `#123`) | шукає в задачах keel, потім у репозиторії, і питає «Це вона?»; сам по собі `#123` ніколи не читається з GitHub: дайте посилання на issue |
| шлях до файлу | читає файл |
| ваші слова | бере їх як задачу й шукає схожі незакінчені задачі |
| нічого | показує незакінчені задачі й питає, яку продовжити або яка нова задача |

Далі одне спільне питання (переказ, «продовження X?» або «нова, правильно?» і запропонована назва),
питання або пропозиція брейншторму, план із гілкою, де працювати (нова гілка від поточної,
рекомендовано; поточна гілка; або ваші власні кроки git, які keel виконує в обох режимах git), папка
задачі й код. Усі випадки, зокрема продовження задачі:
[два способи працювати](workflows.uk.md#почати-задачу-keelstart-task).

## `/keel:end-task`

`/keel:end-task [інструкція]`

| Ви вводите | keel робить |
|---|---|
| `/keel:end-task` | меню: завершити повністю / передати / своя інструкція |
| `/keel:end-task заверши` | перевірка (рівень обираєте ви), виправлення, власне підтвердження Claude Code «задачу <id> виконано?» (щоразу; «так» переносить папку в кошик keel, «ні» лишає задачу активною), git, звіт |
| `/keel:end-task передай` (будь-якими словами: «постав на паузу», «підготуйся до наступної розмови») | лише гейти, оновлення файлу задачі, git, звіт. Задача без власної гілки й без інструкції щодо git: keel спершу питає, куди йде робота (нова гілка, поточна гілка, без коміту або ваша інструкція), і виконує відповідь |
| `/keel:end-task заверши й злий у main` | як «заверши», потім [злиття](workflows.uk.md#злиття-в-головну-гілку) (Claude Code спершу питає, якщо ви не підтвердили автономний git на цьому ПК і не задали `git.ask_before_merge: false`) |
| `/keel:end-task запуш` | питає: завершити чи передати? |

Усі випадки: [два способи працювати](workflows.uk.md#закінчити-задачу-keelend-task).

## `/keel:tasks`

`/keel:tasks [<id> | drop <id>]`

| Ви вводите | keel робить |
|---|---|
| `/keel:tasks` | Показує незакінчені задачі цього робочого дерева й усіх гілок (станом на останній fetch): `<id> · <заголовок>`, далі Джерело, Стан (активна чи передана, як давно, скільки кроків зроблено з усіх, гілка), Далі й Файли; рядок «Базова гілка пішла вперед», коли базова гілка отримала нові коміти після передачі. Задача, передана 30 днів тому або раніше: keel пропонує завершити або прибрати її. Наприкінці: «Продовжити одну: `/keel:start-task <id>`». |
| `/keel:tasks CAN-123` | Показує цю задачу: мета, стан, відкриті питання й наступна дія, у 3-6 рядках. Читає файл задачі й з іншої гілки. |
| `/keel:tasks drop CAN-123` | Пояснює все, що лишила задача: її папку, гілку (локальну, запушену), коміти, яких немає в базовій гілці, змінені файли й документацію серед них. Питає, що прибрати: усе чи які частини. Далі кожне прибирання окремо, папка першою, і сам Claude Code просить вас підтвердити папку й гілку. Папка йде в кошик keel (`/keel:cleanup restore` повертає її); коли її гілка лишається, прибирання комітиться на цій гілці. Гілка видаляється локально (`git branch -D`) і, якщо її запушили, на віддаленому репозиторії; після локального видалення keel друкує команду `git branch <name> <commit>`, яка її повертає, а після віддаленого — останній коміт віддаленої гілки й `git push <remote> <commit>:refs/heads/<name>`, що повертає її, доки цей коміт ще є у вашому репозиторії. Головна й поточна гілки відхиляються (спершу перейдіть на іншу). Зміни, що вже в базовій гілці, лише відкочуються (`git revert`), історія не переписується. У ручному git keel дає команди коміту, гілки й відкату замість того, щоб виконувати їх. |

Приклад списку: [два способи працювати](workflows.uk.md#переглянути-й-прибрати-задачі-keeltasks).

## `/keel:start-session`

`/keel:start-session [файл плану | посилання | опис | як продовжити]`

| Ви вводите | keel робить |
|---|---|
| `/keel:start-session`, коли є нотатка | підсумок, де ви зупинилися, і перша дія |
| `/keel:start-session`, коли нотатки немає | шукає плани й TODO і пропонує, що взяти; коли є незакінчені задачі, підказує `/keel:tasks` і `/keel:start-task` |
| `/keel:start-session docs/plan.md` (або посилання чи опис) | починає нову лінію роботи: пише нотатку, показує її й питає «Почати?», потім створює гілку лінії (у ручному git дає `git switch -c <name>` і чекає); коли нотатка відкрита, а це про іншу лінію роботи, спершу питає «продовжити записану лінію чи почати нову?» |
| `/keel:start-session сьогодні тільки тести` | продовжує за вашою інструкцією |

Усі випадки: [два способи працювати](workflows.uk.md#почати-сесію-keelstart-session).

## `/keel:end-session`

`/keel:end-session [інструкція]`

| Ви вводите | keel робить |
|---|---|
| `/keel:end-session` | перевірка (рівень обираєте ви), нотатка на наступний раз, git, «Наступного разу: ...», щоб ви погодилися або виправили |
| `/keel:end-session продовжимо завтра, підготуйся` | лише гейти, нотатка, git |
| `/keel:end-session запуш і злий у main` | перевірка, нотатка, потім пуш і злиття |
| `/keel:end-session цю лінію закінчено` | перевірка, нотатка, позначена завершеною, потім git як завершення: коміт, оновлення з головної гілки, пуш (автономно); злиття лише тоді, коли ви про нього просите або `git.ask_before_merge` вимкнено |

Усі випадки: [два способи працювати](workflows.uk.md#закінчити-сесію-keelend-session).

## `/keel:cleanup`

`/keel:cleanup [restore [batch] | empty-trash]`

| Ви вводите | keel робить |
|---|---|
| `/keel:cleanup` | Знаходить тимчасові файли, резервні копії, кеші та те, що лишила стара система нотаток, і показує їх трьома групами: **безпечні** (позначені наперед), **перевірити** й **не чіпати** (обидві лише за номером; для пункту «не чіпати» ще одне питання про те, що може зламатися). Переносить лише обране до `.keel/local/trash/<batch>/`. Якщо це зачіпає тести проєкту, запускає їх; червоні → сам повертає партію й запускає знову. Звітує, що перенесено, скільки місця, і як скасувати. Нічого не знайшов → так і каже. |
| `/keel:cleanup restore` | Повертає найновішу партію. |
| `/keel:cleanup restore <batch>` | Повертає цю партію (також папку прибраної задачі). |
| `/keel:cleanup empty-trash` | Каже, що буде видалено остаточно (типово партії віком 30 днів і більше, `cleanup.trash_max_age_days`; або одну названу вами партію за запуск; або все); сам Claude Code просить підтвердити, називаючи, що саме (партії такого віку, одну партію чи все), і тоді видаляє. |

Назавжди видаляє файли лише `empty-trash`; кошик сам ніколи не очищується. (`/keel:tasks drop` ще
й видаляє гілку задачі, після вашого підтвердження.) Секретні файли ніколи не переносяться й не
відкриваються, як і папка, що містить такий файл: keel відмовляє й називає секретний файл. Після
задачі чи сесії keel нагадує про `/keel:cleanup` лише тоді, коли назбиралося досить залишків.

## `/keel:usage`

`/keel:usage` дає посилання на приватну [сторінку «keel usage»](usage-dashboard.uk.md) цього ПК і
відкриває її. Працює в будь-якому проєкті, налаштованому чи ні. Якщо на цьому ПК сторінки ще немає →
каже про це й радить `/keel:configure usage`.

## `/keel:help`

`/keel:help` показує коротку таблицю команд (що робить кожна, як запускати, один приклад) мовою
розмови й один рядок про два напрямки роботи. Нічого не запускає й не читає.
