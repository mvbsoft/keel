# Як працює keel

[English](overview.md)

keel — плагін для Claude Code, який веде вашу роботу над проєктом за набором правил: на старті
розбирається в задачі й складає план, у процесі пише код за вашими стандартами, а наприкінці агенти
перевіряють зміну, keel робить git (або дає готові команди, у ручному режимі) і звітує про витрати.
Ідея: якість як у дорогого процесу, але дешево; кожна перевірка має рівень, і його ціну видно.

keel діє лише в проєкті, який ви налаштували через `/keel:configure`; деінде він не додає правил,
перевірок чи агентів, лише короткі описи своїх команд і агентів, які Claude Code показує для кожного
встановленого плагіна ([встановлення](install.uk.md#що-keel-змінює-на-вашому-пк-і-в-проєктах)).

Ця сторінка показує всю систему коротко; кожен розділ закінчується посиланням на докладну сторінку.

## 1. Дві лінії роботи

У keel два напрямки роботи, і вони не змішуються: що почалося як задача, ведеться через задачі; що
почалося в сесії — через сесії.

| | Задачі | Сесії |
|---|---|---|
| Що це | точкові зміни: баг, тікет, невелика фіча; можна багато одночасно | одна велика робота за планом, день за днем |
| Команди | `/keel:start-task <що завгодно>`, `/keel:end-task [інструкція]`, `/keel:tasks` | `/keel:start-session [план \| опис \| посилання \| нічого]`, `/keel:end-session [інструкція]` |
| Де живе | `.keel/tasks/<id>/`, на гілці задачі | `.keel/next-session.md` |

**Як вибрати:** «готово» за 1-3 підходи → задача; план на тижні з пунктами «на потім» → сесія.

**Спільне для обох:** команди початку й закінчення приймають інструкції звичайними словами, без
слів-аргументів; незрозуміло → keel перепитує; перед кожною дією каже, що зробить.

Докладно: [два способи працювати](workflows.uk.md).

## 2. Початок задачі

`/keel:start-task` читає джерело (посилання ззовні, ключ, який шукається в задачах keel і в
репозиторії, файл або ваші слова) → переказує простими словами (мета, як зрозуміємо, що готово, чого
не робимо) і звіряє це з кодом → ставить одне питання: «продовження X?» або «нова, правильно?» разом
із запропонованою назвою й описом. Коли мета розмита, пропонує брейншторм — тільки з вашого «так».

- **Нова задача:** план (складна — у Plan Mode) разом із гілкою, де працювати: нова від поточної
  гілки (рекомендовано), поточна гілка або ваші власні кроки git → гілка → папка задачі → робота.
- **Продовження:** гілка, файл задачі, свіжість (чи пішла вперед main, чи передано її 7 днів тому або
  раніше), команда перевірки, підсумок і наступна дія.
- **Ключ, який веде сесія:** «це веде /keel:start-session».

Докладно: [почати задачу](workflows.uk.md#почати-задачу-keelstart-task).

## 3. Закінчення задачі

`/keel:end-task` без інструкції показує меню: завершити / передати / своя інструкція.

- **Завершити:** перевірка (рівень обираєте ви) → виправлення → власне підтвердження Claude Code
  «задачу <id> виконано? Її папка `.keel/tasks/<id>/` піде в кошик keel» → так: папка в кошик keel,
  далі git (автономно: коміт, оновлення з main, пуш; крок git, що зупинився до коміту, повертає
  задачу). Ні: задача лишається активною.
- **Передати:** лише гейти → оновлення файлу задачі → коміт, пуш, повернення на базову гілку → звіт. Задача
  без власної гілки спершу питає, куди йде робота.
- Злиття в main — лише за вашою інструкцією (або на завершенні з `git.ask_before_merge: false`).

Докладно: [закінчити задачу](workflows.uk.md#закінчити-задачу-keelend-task); що гарантує кожен крок:
[як поводиться keel](behavior.uk.md).

## 4. Список задач

`/keel:tasks` показує незакінчені задачі з усіх гілок; `/keel:tasks <id>` показує одну;
`/keel:tasks drop <id>` прибирає те, що лишила задача, кожну частину після окремого «так».
Докладно: [команда /keel:tasks](commands.uk.md#keeltasks).

## 5. Сесії

`/keel:start-session` продовжує з нотатки або починає нову лінію з плану, опису чи посилання; без
нотатки пропонує роботу й ніколи сам не починає задачу. `/keel:end-session` перевіряє роботу сесії,
оновлює нотатку й робить git; `/keel:end-session продовжимо завтра, підготуйся` запускає лише гейти;
`/keel:end-session запуш і злий у main` ще й зливає.
Докладно: [почати сесію](workflows.uk.md#почати-сесію-keelstart-session),
[закінчити сесію](workflows.uk.md#закінчити-сесію-keelend-session).

## 6. Звіт наприкінці

Один для обох напрямків: **Зроблено** → **Перевірка** (таблиця: знайдено / виправлено / лишилось,
гейти) → **Git** → **Що далі** → **Витрати** (таблиця, по рядку на учасника: запити, токени, $ і
частка від усієї суми; на підписці — частка лімітів плану).
Докладно: [підсумковий звіт](workflows.uk.md#підсумковий-звіт) і [панель витрат](usage-dashboard.uk.md).

## 7. Нотатка передачі

Один формат для обох напрямків: мета, наступна дія, стан (✅ / ◐ / ⚠ / ⬜), файли, рішення і чому, що
не спрацювало, відкриті питання, як перевірити. До 150 рядків; оновлюється, а не переписується.
Докладно: [що входить у передачу](workflows.uk.md#що-входить-у-передачу).

## 8. Перевірка

| Рівень | Хто перевіряє | Ціна |
|---|---|---|
| Лише гейти | тести, лінтери, типи, сканери проєкту | ≈$0.2 |
| Basic | один рецензент (Haiku) + до 2 перевіряльників | ≈$0.25-0.5 |
| Standard | карта контексту (Haiku), рецензент, мисливець за помилками, архітектор, QA, рецензент тестів, до 4 груп спеціалістів + до 5 перевіряльників, суддя | ≈$1.4-4.3 |
| Maximum | двоє мисливців за помилками, QA і «спробуй зламати», безпека завжди, три перевіряльники на кожну критичну знахідку, суддя; переважно Opus | ≈$2.7-7.6 |

Агенти працюють на Sonnet, якщо вище не названо іншу модель. На Opus працюють: група безпеки
(Standard і Maximum), архітектор Standard, коли зміна має ознаки архітектури (нові файли, файли понад
попередження про розмір), і перевіряльники Standard для знахідок мисливця за помилками й безпеки. Коли
«Allow Opus» вимкнено, кожен із них працює на Sonnet.

План уже називає ймовірний рівень; наприкінці keel пропонує рівень за фактичною зміною, і він може
відрізнятися; обираєте ви. Перевіряльники пробують спростувати серйозні знахідки — стільки, скільки
дозволяє ліміт рівня. Знахідка, яку QA довів командою, що падає, не потребує перевіряльника: keel
запускає цю команду ще раз, і якщо вона більше не падає, знахідка стає «неясною» (команда, яку keel не
може запустити повторно, лишається «доведеною» з позначкою «не запускалася повторно»). Пункти «можна виправити»
показуються як «не перевірено». Після виправлень повторно перевіряється лише виправлене.

Докладно: [перевірка](verification.uk.md).

## 9. Делегування

Великий план keel пропонує віддати агентам-виконавцям, по одному на крок, кожен на моделі, якої
потребує крок (Haiku, Sonnet або Opus). Головна розмова приймає кожен крок після його тестів.
Докладно: [економія витрат](cost-optimization.uk.md#5-пороги-делегування) і
[під капотом](under-the-hood.uk.md#делегування).

## 10. Git

Ручний режим: keel не виконує жодного кроку git, про який ніхто не просив; він дає готові команди й
повідомлення коміту. Автономний: гілки, коміти, оновлення, пуш; підтверджується один раз для проєкту
на кожному ПК. В обох режимах виконуються гілка, яку ви обрали на початку задачі, і ваші власні кроки
git. Секретні файли не потрапляють у коміти keel, без підписів ШІ, без force-push, ніколи не коміт у main напряму; захищена main →
pull request.
Докладно: [git у кожному режимі](workflows.uk.md#git-у-кожному-режимі).

## 11. Інші команди

`/keel:configure` налаштовує проєкт (швидко або докладно) або цей ПК; `/keel:cleanup` переносить
залишки в кошик keel і повертає їх; `/keel:help` показує таблицю команд.
Докладно: [команди](commands.uk.md) і [налаштування](settings.uk.md).

## 12. Що працює у фоні

У налаштованому проєкті: робочі стандарти в кожній розмові, попередження перед тим, як Claude Code сам
стисне розмову, підказки для дорадчих навичок і перевірка, що блокує підписи ШІ в комітах і pull
request. Поки працює keel: модель кожного агента keel, власні скрипти keel без запиту дозволу,
підтвердження Claude Code для кроків, які важко скасувати, і облік витрат агентів. На всьому ПК: запис
витрат і статус-рядок.
Докладно: [під капотом](under-the-hood.uk.md).
